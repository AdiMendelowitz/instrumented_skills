## Batch API, check this first

Asynchronous processing within 24 hours at 50% off both input and output. Stacks with caching. No prompt change, no quality risk, no format change. For any scheduled or non-interactive workload this is the largest single lever available and it requires the least work.

It does not apply to anything a user waits on.

## Caching mechanics

Caching is prefix-based over tools, then system, then messages, up to and including the block marked with `cache_control`. A single character differing before the breakpoint is a miss.

**Minimum cacheable length is model-dependent and is the most common silent failure.** 512 tokens for Fable 5.1, Opus 5.5, Opus 5, Sonnet 5.5, Fable 5 and Haiku 5.5; 1,024 for Sonnet 5; 4,096 for Haiku 4.5. Below the threshold the request succeeds and nothing is cached. [first-party, 2026-10-18; the 4,096 recorded for Opus 5 on 2026-08-04 was stale] A pipeline pinning Haiku for extraction and applying a 1,024-token rule caches nothing on that tier, silently.

**Verifying a cache actually works.** Cache diagnostics (beta) has the API compare consecutive requests and report exactly where the prefix diverged; reach for it first. [first-party, 2026-09-28] Failing that, send the request and read `cache_creation_input_tokens` on the first call and `cache_read_input_tokens` after. Zero reads means the breakpoint was discarded or the prefix changed. Record the answer per model. [measured]

**Structural limits that govern real hit rates.** [all first-party, 2026-09-28]

- Four explicit `cache_control` breakpoints per request, maximum. Automatic caching consumes one slot.
- The lookback checks roughly 20 previous content-block boundaries before your breakpoint. It does not scan backwards for stable content and cache it: it only finds entries earlier requests already wrote, and writes happen only at breakpoints. A breakpoint on a block that changes every request (a timestamp, the user message) writes a fresh cache every time and never reads. Move the marker to the last block that stays identical, and add an earlier marker once a prompt exceeds ~20 blocks.
- Tool definitions render first, so a breakpoint on the last tool caches the tool block, and changing any tool invalidates system and messages downstream.
- Cache validity breaks on more than text: `tool_choice`, image usage, thinking configuration, and effort settings must stay consistent across calls.
- Server-tool use inserts an automatic 5-minute breakpoint, so writes can appear under `cache_creation.ephemeral_5m_input_tokens` even when your own markers use the 1-hour TTL.

**Automatic caching.** A top-level `cache_control` field caches the last cacheable block and slides the breakpoint forward as the conversation grows. It is the right default for multi-turn work and removes most manual breakpoint management. [first-party, 2026-09-28]

**Hit rate as a monitor.** Below roughly half on long-context work signals a misplaced breakpoint. [secondary, 2026-08-04]

**Prices are multipliers on base input:** 5-minute write 1.25x, 1-hour write 2x, read 0.1x, except reads on Opus 5.5 and Sonnet 5.5 at 0.05x and on Fable 5.1 and Mythos 5.1 at 0.025x [first-party, 2026-10-18]; `rates.json` carries these as `cache_read_mult`. On the prefix, one write plus one read costs 1.35x against 2x for two uncached sends, so the first re-read already breaks even on the 5-minute tier; the 1-hour tier breaks even on the second re-read (2.2x against 3x). A single-shot call that pays the write premium and never reads costs more than not caching. Output tokens bill at full rate regardless.

**TTL.** 5 minutes by default, refreshed on each hit. A 1-hour cache is available with `"cache_control": {"type": "ephemeral", "ttl": "1h"}`. Where both are used in one request, longer TTLs must appear before shorter ones. The 1-hour option removes the constraint that a whole pipeline must finish inside one 5-minute window.

## Correct caching syntax

`cache_control` goes on a block in the `system` list, not on user content.

```python
response = client.messages.create(
    model=MODEL,                      # explicit, pinned, never an implicit default
    max_tokens=500,
    temperature=0,
    system=[
        {"type": "text", "text": STATIC_INSTRUCTIONS,
         "cache_control": {"type": "ephemeral"}},        # stable prefix, cached
        {"type": "text", "text": f"Current date: {today}."},  # dynamic, not cached
    ],
    messages=[{"role": "user", "content": user_message}],
)
```

Split a system prompt into static and dynamic blocks and mark only the static one. Parameterising the static block with per-request data destroys the hit rate; put that data in `messages` instead.

## Cost modelling for the audit

Rank on modelled spend, with correct units. Rate per token is the per-million figure divided by 1e6:

```bash
cd tools
python cost.py cost --model claude-sonnet-5 --in 2400 --out 350 --calls 1200 --site pipeline.py::classify --log
```

`cost.py` reads the dated rates in `rates.json` and refuses once they expire; never paste a per-token constant into audit code, since a hardcoded example rate is how this file once carried the $3/$15 Sonnet figure that never took effect.

Modelled cost per site is calls times the per-call figure. Rank descending and work down until cumulative modelled cost reaches 80% of the total. That is a stopping rule you can check, unlike a fixed "top 20%".

## Cost tracking in production

```python
logger.info(
    "llm | model=%s | in=%d | out=%d | cache_read=%d | cache_write=%d",
    response.model,
    response.usage.input_tokens,
    response.usage.output_tokens,
    getattr(response.usage, "cache_read_input_tokens", 0),
    getattr(response.usage, "cache_creation_input_tokens", 0),
)
```

The flat `cache_creation_input_tokens` field under-reports where server tools inserted their own 5-minute breakpoint. Where `usage.cache_creation` is present, read its `ephemeral_5m_input_tokens` and `ephemeral_1h_input_tokens` members and log both, falling back to the flat field only when the nested object is absent.
